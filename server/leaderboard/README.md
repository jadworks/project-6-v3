# Vice Bay guest leaderboard

`completed-contracts-v1` / `v1` ranks the highest number of contracts completed in a single play session. Initialize the session count to zero on reload; increment it only for actually completed contracts during that session. Never import a lifetime count or an old local save. At each contract's start issue a fresh ranked ticket; submit at that contract's successful completion with the session count and **that contract's duration**. Do not submit failed, abandoned, or ineligible contracts. Each ticket is single-submission; the backend retains the player's best reported session count, rather than summing submissions. Equal scores keep the earlier best.

Score bounds are **1–1,000 contracts**; duration is **1,000–1,800,000 ms**. Run tickets expire 30 minutes after issuance and must be submitted before expiration. Duration must be an integer, and the backend permits only up to five seconds beyond its observed elapsed time. Client-reported data is casual and is not verified gameplay or anti-cheat. Never use it for prizes or claims of competitive fairness.

The client must create or recover its guest identity explicitly. Never invent a rank. Continue local play if online services fail. Keep the same ticket and payload for retry, and show the actual API result; accepted score and board refresh are separate outcomes. Keep `client_upgrade_required` latched until reload while preserving offline progress and allowing board reads.

Guest identity is an opaque server-issued token stored locally; it expires after 30 days, and clearing storage or changing devices can lose the identity. This is not cross-device account recovery. Never expose database credentials. The fixed namespace is server-owned; `production` exists on separate managed checkpoint and live database branches.

Before public launch, establish and review an operational retention policy: prune stale rate-limit buckets and expired unsubmitted runs, retain accepted receipts for the advertised retry/audit window, and retain expired guest players referenced by scores. Do not delete best-score rows as part of releases or rollback. Review abuse limits for expected traffic. API readiness and a genuine ranked run must be validated in the selected checkpoint Preview and the published site before claiming online acceptance; the database-independent `/api/health` alone is insufficient.

Database migrations are finite and ordered. `npm --prefix server run db:migrate:leaderboard` applies the checked-in additive files and records their hashes in the project database; startup and publishing never migrate or seed. Do not edit an applied migration, change an existing board's rules, or point this command at any database other than this game's managed database. New scoring rules require a new board ID and additive migration.
